# Plan de Pruebas Maestro (Master Test Plan) - IEEE 829 ## 1. Identificador, Introducción y Alcance **Identificador del Documento:** MTP-SBAC-V1.0   **Proyecto:** Sistema Básico de Administración de Configuración (SBAC)   **Fecha:** 15 de Mayo de 2026   **Versión:** 1.0   **Introducción:**   El presente Plan de Pruebas Maestro define la estrategia, alcance, recursos y cronograma de las actividades de aseguramiento de calidad (QA) y pruebas de software para el proyecto universitario SBAC (Sistema Básico de Administración de Configuración). SBAC es una herramienta de Interfaz de Línea de Comandos (CLI) desarrollada en Python, diseñada para proporcionar funcionalidades simplificadas de control de versiones y administración de configuración análogas a Git.  **Alcance de las Pruebas:**   Las pruebas se centrarán exhaustivamente en validar la correcta ejecución, robustez y manejo de errores de los módulos críticos del sistema que componen el flujo de trabajo del usuario. Las áreas prioritarias incluyen: *   **Gestión de Repositorio:** Inicialización y configuración del entorno de trabajo local (`sbac init`). *   **Control de Versiones (Flujo Básico):** Rastreo de archivos y confirmación de cambios en el repositorio local (`sbac add`, `sbac commit`, `sbac status`). *   **Gestión de Historial y Trazabilidad:** Consulta del registro de confirmaciones (`sbac history`) y comparación de versiones (`sbac diff`). *   **Gestión de Líneas Base y Restauración:** Creación de puntos de control (`sbac baseline`) y restauración a estados previos (`sbac checkout`). ## 2. Estrategia de Pruebas El enfoque metodológico para la validación del SBAC combinará múltiples técnicas para garantizar una cobertura integral del código y de las funcionalidades requeridas: *   **Pruebas de Caja Negra (Black-Box Testing):** Se validarán los requerimientos funcionales desde la perspectiva del usuario final. Esto implicará la ejecución de los comandos CLI mediante scripts o de forma manual, evaluando las salidas estándar (stdout), salidas de error (stderr) y los códigos de salida (exit codes) sin examinar la estructura interna del código Python. Se aplicarán técnicas como partición de equivalencia y análisis de valores límite para los argumentos de los comandos. *   **Pruebas de Caja Blanca (White-Box Testing):** Se realizarán pruebas estructurales directamente sobre el código fuente en Python (mediante frameworks como `pytest` o `unittest`). El objetivo es alcanzar una cobertura de código óptima (Code Coverage) examinando la lógica interna, rutas de ejecución, estructuras de datos subyacentes y manejo de excepciones en las funciones que operan los comandos del SBAC. *   **Pruebas de Regresión (Regression Testing):** A medida que se integren nuevos módulos (e.g., desarrollar `sbac checkout` después de `sbac commit`), se ejecutarán baterías de pruebas automatizadas previas para asegurar que las modificaciones o nuevas implementaciones no introduzcan defectos en el código previamente validado y estable. ## 3. Criterios de Aceptación / Éxito Para considerar el proceso de pruebas como exitoso y el software SBAC apto para su entrega, se deben cumplir los siguientes criterios métricos y cualitativos: *   **Cobertura Funcional y Tasa de Éxito:** Se requiere una tasa de éxito funcional mínima del **95%** en la ejecución de los casos de prueba planificados. *   **Niveles de Defectos:** **Ausencia total (0%) de fallos críticos o bloqueantes** (severidad Alta/Crítica) que comprometan la integridad del repositorio, resulten en pérdida de datos o generen cierres inesperados (crashes) del sistema. *   **Estabilidad:** Los defectos menores o cosméticos (severidad Baja) detectados no deben superar el 5% del total de pruebas ejecutadas y deben contar con un plan de mitigación o justificación. ## 4. Entregables de Pruebas (Según Estándar IEEE 829) Como parte del proceso formal de documentación de QA, se generarán y mantendrán los siguientes artefactos: 1.  **Test Plan (Plan de Pruebas Maestro):** El presente documento (MTP-SBAC-V1.0). 2.  **Test Design Specification (Especificación de Diseño de Pruebas):** Detalle de las condiciones de prueba, enfoques específicos por módulo y datos de prueba requeridos. 3.  **Test Case Specification (Especificación de Casos de Prueba):** Catálogo detallado de los casos de prueba con entradas, pasos de ejecución y resultados esperados. 4.  **Test Log (Registro de Pruebas):** Bitácora cronológica con los detalles de la ejecución de las pruebas. 5.  **Test Incident Report (Reporte de Incidentes/Defectos):** Documentación formal de cualquier desviación o error encontrado durante las pruebas. 6.  **Test Summary Report (Reporte Resumen de Pruebas):** Informe final evaluando los resultados de las pruebas contra los criterios de aceptación estipulados. ## 5. Cronograma por Sprints y Asignación de Responsables El proyecto se desarrollará a lo largo de un ciclo de 4 semanas (Sprints), con la siguiente distribución de responsabilidades para el equipo de 5 personas: *   **Sprint 1 (Semana 1) - Planificación y Configuración Base:** *   **Actividades:** Definición del Plan de Pruebas, configuración del entorno de QA, diseño de pruebas para comandos iniciales (`init`, `add`). *   **Responsables:** Persona 5 (QA Lead/Documentador) para el MTP; Persona 1 y Persona 2 para diseño de casos iniciales. *   **Sprint 2 (Semana 2) - Pruebas Funcionales Core:** *   **Actividades:** Ejecución de pruebas Caja Negra y Blanca para comandos centrales (`status`, `commit`, `history`). Registro de primeros incidentes. *   **Responsables:** Persona 3 y Persona 4 (Ejecución y automatización de pruebas); Persona 5 (Supervisión y Logs).  *   **Sprint 3 (Semana 3) - Funcionalidad Avanzada y Regresión:**     *   **Actividades:** Pruebas de funcionalidades complejas (`baseline`, `diff`, `checkout`). Primera ronda de Pruebas de Regresión sobre el Sprint 2.     *   **Responsables:** Persona 1, Persona 2, Persona 3, Persona 4 (Distribución de módulos avanzados).  *   **Sprint 4 (Semana 4) - Estabilización y Cierre:**     *   **Actividades:** Pruebas de Regresión finales, resolución de defectos críticos, elaboración del Reporte Resumen de Pruebas (Test Summary Report).     *   **Responsables:** Todo el equipo (Resolución y re-testing); Persona 5 (Consolidación de entregables y reporte final).  ---
